# KAI PLAY — 扑克牌实体材质 V11 / 细节精修 V12 / 授权牌面 V13

> 状态：V11 材质已采用，V12 细节精修与 V13 CC0 宫廷牌/大小王已实施<br>

## 目标

V11 让牌面呈现温润、轻微压纹的实体卡纸触感，同时保留 KAI PLAY 既有的实时牌局、语义化点数、人物牌与无障碍能力。材质只负责纸张表面，不把点数、花色、牌局状态或交互烘焙进图片。V13 只替换中央人物插画：四花色 J/Q/K 改用逐花色授权素材，大小王改用两套可区分的授权衍生图；牌值、花色、ARIA 和交互仍由 DOM 决定。

用户在大厅预览、斗地主手牌、桌面出牌、底牌和炸金花中应感知到同一副牌；尺寸缩小时，信息优先级必须从“完整实体感”平滑退化到“首先认清牌”。

## V12 精修决策

V12 不增加第二套牌面图片，而是在同一副动态卡牌上修正真实感和操作一致性：

- 7、8、10 采用更接近实体扑克牌的上下中央点位，底部中央花色保持倒置。
- 每个 rank/suit 组合获得稳定的卡纸裁切坐标，避免整手牌看起来使用同一块重复贴图。
- J/Q/K/Joker 的米色底块改为透明，让人物印刷直接落在共享卡纸上；红色人物牌显式使用 `contain`，不再被旧级联裁切。
- Full/Compact/Micro 按卡牌自身宽度判断。52px 手牌属于 Compact，保留完整点数和人物轮廓；只有低于 40px 的飞牌或极小牌堆隐藏中央细节。
- 牌背取消二次深色 multiply 压暗，由轻微 soft-light 让纸纹作用于原有 K 纹、金线和徽章。
- 非交互牌不再显示手型或伪悬停；选中牌在 hover 下保持抬起和描边；键盘焦点使用内深外浅双环并提升到整手牌最上层。
- 内容摘要文件使用真实 SHA-256 前缀命名，并获得一年 `immutable` 缓存；运行时材质预算门禁收紧到 80 KiB。

## 牌面分层

从底到顶保持以下职责边界：

1. 暖白纯色：网络失败、图片解码失败和高对比场景的可靠底色。
2. 卡纸材质：只提供微纤维与压纹，不承担方向性强光和牌面信息。
3. 克制的光照渐变：表达纸张厚度与桌面接触，不制造塑料高光。
4. 边缘、内描边与阴影：区分相邻重叠牌；阴影不能盖住下一张牌的点数角标。
5. 牌面信息：上下角标、中央点数和 KAI 签名保持实时 DOM；J/Q/K/Joker 中央图形按语义属性选择本地 V13 SVG。
6. 交互状态：焦点、选中、禁用和可点击状态位于最上层，并且不能只依赖颜色。

正面与牌背始终使用 `9:13` 比例。同一屏内不得混用明显不同的纸白、圆角或边缘厚度。

## Full / Compact / Micro

三个模式描述最终可见信息，不要求新增同名 DOM 类；实现可按组件上下文或实际渲染宽度选择。

| 模式 | 参考牌宽 | 典型场景 | 必须保留 | 可简化 |
|---|---:|---|---|---|
| **Full** | ≥ 56 CSS px | 大厅主视觉、桌面出牌区、炸金花亮牌 | 卡纸纹理、上下角标、完整点数或双头人物、KAI 签名、边缘与接触阴影 | 不得简化主要牌面信息 |
| **Compact** | 40–55 CSS px | 标准手牌、底牌、手机出牌区、目录预览 | 左上角标、完整花色语义、可识别点数或人物轮廓、材质与边缘分离 | 可降低纹理/阴影强度；签名可隐藏；右下角标仅在不碰撞时保留 |
| **Micro** | < 40 CSS px | 发牌飞牌、对手密集牌堆 | 左上点数与花色、红黑语义、暖白实体边缘 | 隐藏签名、右下角标和中央细节；纹理不得形成噪点或降低识别度 |

Micro 是视觉尺寸，不等于交互热区。可选择的牌仍需提供至少 44×44 CSS px 的可达热区或等效的无遗漏选择机制；重叠扇形中的每张牌必须能被键盘和指针独立选中。

## 真实性边界

- 不把未经来源与许可核验的实体扑克牌照片、品牌花纹、水印或赌场筹码合成进牌面；仅允许清单中逐文件固定哈希的 CC0 衍生素材。
- 不宣称该纹理来自某个真实制造商、纸张克重、涂层工艺或摄影扫描；它是 KAI PLAY 的原创数字材质。
- 图片不包含点数、花色、胜负、选中状态或可点击提示；这些内容必须来自当前牌局状态。
- 四种花色依靠符号与颜色共同区分；红桃/方块不能只以“红色”表达，黑桃/梅花也不能只以“黑色”表达。
- 大小王必须有不同文本与语义标签；装饰牌应 `aria-hidden`，真实牌应提供准确 `aria-label`。
- 材质升级不得引入现金、筹码、下注或其他不属于 KAI PLAY 当前玩法的赌场信号。

## 可读性与交互

- 主要角标文字与牌纸背景的对比度目标不低于 4.5:1；材质纹理不能穿透到影响字形边缘。
- J、Q、K、A、2 与大小王在 Compact 和 Micro 中必须一眼可区分，不能仅依靠中央插画。
- 手牌重叠时，每张牌至少露出完整左上角标；选中态使用位移加描边/阴影，不只改变颜色。
- `:focus-visible` 必须清晰且不被相邻牌遮挡；禁用态仍保留点数可读性。
- Reduced Motion 下取消发牌、抬牌和扇形过渡，但不隐藏牌或交互反馈。
- 材质加载失败、图片关闭或高对比模式下，牌面仍能凭底色、边框、文字和符号完成游戏。

## 自动化验收

1. 资产存在且保持 512×512、JPEG、≤ 80 KB；服务端返回 `image/jpeg`、ETag 与既定 `/assets/*` 缓存头。
2. CSS 使用本地相对路径引用卡纸，并保留纯色/渐变回退；不得出现外部图片 URL。
3. 正面和牌背保持 `9:13`；14 个 V13 J/Q/K/Joker SVG 必须全部存在、文件名摘要前缀与最终 SHA-256 一致，并且不含脚本、事件处理器、`foreignObject` 或外链资源。
4. 渲染契约覆盖 3–10、A、2、J/Q/K、大小王和四种花色，验证点数数量、红黑类、上下角标、ARIA 与选中状态。
5. Full、Compact、Micro 的源码或组件契约必须明确；Micro 不得隐藏唯一可识别的左上角标。
6. Docker 产物必须实际包含卡纸、牌背和 `web/assets/cards` 的 14 张人物牌资产；不能只在宿主机预览服务中通过。
7. `docs/asset-provenance/playing-cards.json` 必须覆盖 14 个实际运行时文件，逐项校验最终 SHA-256、上游 SHA-256、来源、CC0-1.0 与修改记录；`THIRD_PARTY_NOTICES.md` 和 `LICENSES/CC0-1.0.txt` 必须随发布源码保留。

## 发布门禁

以下任一情况阻止发布：材质未加载时牌面消失；Compact/Micro 无法辨认点数；红黑花色只靠颜色；人物牌被裁切或上下颠倒；大小王共用同一视觉配色；牌背与正面比例不一致；资产请求 404/MIME 错误；同一状态的牌在大厅、斗地主和炸金花使用不同材质系统；任一 V13 文件缺少来源/许可/修改记录或其最终哈希与 provenance 不一致。
